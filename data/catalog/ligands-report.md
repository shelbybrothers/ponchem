## Method, and how each field was obtained

1. `pubchemCid`, `formula`, `mw`, `inchiKey` and the reference isomeric SMILES: PubChem PUG REST name lookup,
   `GET https://pubchem.ncbi.nlm.nih.gov/rest/pug/compound/name/<name>/property/MolecularFormula,MolecularWeight,SMILES,ConnectivitySMILES,InChIKey,IUPACName/JSON`.
   The first CID returned is used. A guard compares the returned formula with the formula expected for the
   named compound; on a mismatch the candidate is dropped, not corrected by hand. Salts (a `.` in the SMILES) are dropped.
2. `ccd`, `ccdName`: RCSB search API, chemical service, `POST https://search.rcsb.org/rcsbsearch/v2/query` with
   `{"query":{"type":"terminal","service":"chemical","parameters":{"value":<PubChem SMILES>,"type":"descriptor","descriptor_type":"SMILES","match_type":"graph-exact"}},"return_type":"mol_definition"}`,
   falling back to `match_type: graph-relaxed` (score 1.0 hits only). Each hit is checked against
   `GET https://data.rcsb.org/rest/v1/core/chemcomp/<ID>` (InChIKey skeleton must equal PubChem's; `chem_comp.name` is recorded as `ccdName`).
3. Coordinates, in priority order:
   - `rcsb-ccd:<ID>`: `GET https://files.rcsb.org/ligands/download/<ID>_ideal.sdf`, accepted when RDKit's canonical SMILES
     of the component equals the PubChem SMILES and every stereo element defined in the PubChem record agrees with the
     stereo perceived from the ideal 3D coordinates (`AssignStereochemistryFrom3D`).
   - `pubchem-3d:<CID>`: `GET https://pubchem.ncbi.nlm.nih.gov/rest/pug/compound/cid/<CID>/SDF?record_type=3d`, same checks.
     Used when the CCD component matches the skeleton but not the stereo or tautomer form (the note says so).
   - `rdkit-etkdg:<CID>`: RDKit ETKDGv3 (seed 20260922) plus MMFF94 minimization from the PubChem isomeric SMILES, when
     PubChem has no 3D record (404) and no CCD component fits.
4. Every SDF: parsed with RDKit (sanitized, explicit H kept for stereo perception), 3D check (z spread, not all zero),
   heavy atoms 10..64, exactly one fragment, then written back through RDKit with explicit hydrogens removed, kekulized
   Flat molecules (no stereocentre, no sp3 atom with three or more heavy neighbours: flat aromatics, quinones, coumarins,
   all trans polyenes) legitimately come with coordinates in one plane from both sources; those coordinate sets are kept and
   rotated by one fixed rigid rotation (35 deg about x, 25 deg about y) so no file has z identically zero. Internal geometry is
   untouched. A planar coordinate set for a molecule that cannot be flat is rejected as a 2D drawing.
   bond block, title line = KEY, property block KEY, NAME, SOURCE, SMILES, FORMULA, MW, HEAVY_ATOMS, ROTATABLE_BONDS
   (RDKit strict count). The written file is re-read and must give the same canonical SMILES and atom count.
   Atom order is the source file's heavy-atom order, so a rerun reproduces the same topology.
5. `formula` and `mw` in the JSON are RDKit's values for the saved molecule; the script drops the ligand if the formula
   differs from PubChem's or the weight differs by more than 0.6.
6. `plant`, `latin`, `class`, `mechanism`, `drug`, `origin` are curator input (hedged wording, no dashes, ASCII only, gated in code).
